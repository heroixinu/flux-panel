# 默认数据库切换 PostgreSQL 的可行性与执行计划

评估日期：2026-11-24；代码基准：`b83f6c0`。本文保留实施前评估；当前操作方式及已实现工具见 [PostgreSQL 安装、迁移与恢复](postgresql-operations.md)。

## 结论与范围

**可行，但不能只替换 JDBC 驱动和 Compose 镜像。** 数据模型以整数、字符串和时间戳为主，业务 SQL 大部分由 MyBatis-Plus 生成，手写 SQL 较少；不过 `user` 保留字、字符串与数字比较、不同排序规则、历史表结构差异以及安装脚本的升级顺序都是切换阻塞项。工作量评估为 **中等偏高**：新安装约 3–5 人日，既有数据迁移、回滚演练和发布验证再约 4–7 人日；依赖真实历史数据、节点上报行为和测试环境，估算不含排队及大数据量迁移时间。

建议新版本的新安装默认使用 PostgreSQL 16，**现有 MySQL 实例必须经过独立的停机迁移后才切换**。新后端首版仅以 PostgreSQL 为运行目标；迁移期间保留旧版 MySQL 镜像、配置和数据作为回退路径，不承诺长期双数据库运行，也不做双写或在线迁移。PostgreSQL 镜像和后端镜像在发布时固定经验证的版本及 digest，数据库只接入内部网络。前端、移动端和 GOST 协议保持兼容。

## 当前代码证据与影响

| 位置 | 现状及实施影响 |
| --- | --- |
| `springboot-backend/pom.xml`、`src/main/resources/application.yml` | Spring Boot 2.7.18、MyBatis-Plus 3.4.1，只有 MySQL 驱动；JDBC URL 固定 3306，含 MySQL 专有参数。需要 PostgreSQL 驱动、5432 配置及真实集成测试。 |
| `springboot-backend/src/main/java/com/admin/entity/User.java`、`UserServiceImpl.java`、`OpenApiController.java` | 表和列均名为 `user`，且登录、用户名唯一性检查、开放 API 直接使用 `.eq("user", ...)`。PostgreSQL 的 `user` 是关键字；只改建表无法修复自动生成 SQL 和条件。 |
| `springboot-backend/src/main/java/com/admin/controller/FlowController.java` | 从 service ID 拆出字符串后，直接用于整数 `id`、`user_id`、`tunnel_id` 条件；MySQL 可能隐式转换，PostgreSQL 需验证并在应用侧安全解析为数值。影响流量上报和额度控制。 |
| `springboot-backend/src/main/resources/mapper/{Forward,User,UserTunnel}Mapper.xml` | 少量 JOIN 和驼峰别名；须验证 PostgreSQL 折叠未引用别名后 MyBatis DTO 映射、空值及查询结果。`MybatisPlusConfig.java` 的分页插件未固定方言，需要验证 PostgreSQL 分页和 count。 |
| `gost.sql` | 8 张表，含 MySQL 反引号、`AUTO_INCREMENT`、`LONGTEXT`、引擎和字符集语法，含管理员及 `vite_config` 初始数据。不能直接给 PostgreSQL 执行。 |
| `panel_install.sh` | 下载固定 1.4.2 资源；更新时覆盖 Compose、`down/pull/up` 后才执行大量 MySQL DDL；健康检查、导出依赖 `gost-mysql`/`mysqldump`，卸载含 `--volumes`。迁移前必须调整控制流，防止空库启动、误删卷或遗漏备份。 |
| `.github/workflows/docker-build.yml`、两个 Compose 文件 | 1.4.2 镜像和 release 资源被固定引用；当前 CI 构建跳过测试。版本、初始化 SQL、脚本、镜像必须作为同一发布集发布。 |
| `springboot-backend/src/main/java/com/admin/CodeGenerator.java` | 开发代码生成器仍固定 MySQL，需同步调整或明确废弃，不能误认为仅运行配置受影响。 |

还要以实际源库为准：`gost.sql` 的 `statistics_flow.id` 是 `int`，而 `panel_install.sh` 对历史库新建该表时使用 `bigint`；`traffic_ratio` 精度、监听地址默认值和字段是否可空也可能随升级路径不同。现有脚本甚至会删除历史列，不能在迁移前直接对生产库盲目重跑。Compose 当前使用 `utf8mb4_unicode_ci`，历史列可能为 `utf8mb4_general_ci`；用户名查找、唯一性及 `vite_config.name` 唯一键在 PostgreSQL 下可能出现大小写、重音或空格比较差异。登录和开放 API 是外部契约，不能静默改变。

## 实施方案

### 1. 先建立兼容性基线

1. 在隔离环境收集有代表性的全新 1.4.2 库和不同历史升级库；记录 MySQL 版本、实际表/列/索引/默认值/字符集与排序规则、行数、最大 ID、NULL 分布和表外对象。先备份恢复演练，任何真实实例不运行现有更新脚本。
2. 建立可重复的 Java 21 + PostgreSQL 16 集成环境，同时保留 MySQL 5.7 基线进行行为比较。当前 `AdminApplicationTests` 基本为空，CI 和 Docker 构建使用 `-DskipTests`，不能视为兼容性证据。
3. 检查实际数据中的整数范围、非法文本（如 PostgreSQL 不接受的 NUL）、超长值、缺失列、额外列、重复用户名及排序规则等价冲突；清单和处置方案经实例负责人确认。未知历史结构、数据丢失或列类型收窄一律中止，不自动截断、删除或填充业务数据。

### 2. 后端与 PostgreSQL 表结构

1. 在 `pom.xml` 引入 `org.postgresql:postgresql` runtime 驱动，使用 Spring Boot 管理的兼容版本；`application.yml` 改为 PostgreSQL JDBC URL，提供 `DB_HOST`、`DB_PORT`（默认 5432）、`DB_NAME`、`DB_USER`、`DB_PASSWORD`，移除 MySQL 专有参数。保持现有连接池及 `SELECT 1`，验证时区和 UTF-8；生产外部数据库的 TLS 方式由部署配置明确指定。
2. 推荐将数据库表 `user` 映射为 `app_user`、列 `user` 映射为 `username`：在 `User` 上用 `@TableName` / `@TableField` 指定映射，Java 属性、DTO、JSON 和 JWT 中 `user` 保持原样；将 `UserServiceImpl` 与 `OpenApiController` 现有三处字符串条件改用正确列名，并全局搜索其他 SQL。迁移时显式执行旧表/列到新表/列的映射。优先避免引号贯穿所有生成 SQL。
3. 检查所有 Wrapper 中以字符串绑定数值列的条件，尤其 `FlowController`：在可信边界解析 service ID，处理非法格式和溢出，禁止将非法输入当作合法 ID；保持现有 API 错误/节点协议语义，并测试查询和原子流量更新。复核所有 `setSql`、分页、批量保存、自动生成主键、NULL 更新和事务异常，不假设跨数据库行为一致。
4. 新增版本化 PostgreSQL 建表文件，例如 `gost-postgresql.sql`：逐列保留 8 张表的实际目标类型、非空、默认值、主键及 `vite_config.name` 唯一约束；`longtext` 用 `text`，数字与 `decimal` 保持精度，自增列使用 `GENERATED BY DEFAULT AS IDENTITY` 以允许迁移显式 ID。保留毫秒时间戳类型，不转换为日期类型。明确 `statistics_flow.id` 对历史 bigint 数据的容量，涉及其他 Java `Integer` ID/引用列必须先做范围核验，不作静默收窄。验证所有实体 `IdType.AUTO` 能返回 ID。
5. 新安装初始化脚本保留当前管理员及配置种子行为；迁移目标库**只建结构，不插种子**，防止 ID/唯一键冲突或产生第二个管理员。确认 Compose 初始化脚本只在空数据目录首次执行，版本升级不能依赖它重复运行。为后续 PostgreSQL 架构升级提供按版本执行、可重复检查并在失败时停止的 SQL；本次不引入迁移框架，除非实现时证明必需。
6. 对用户名及配置名制定比较契约：先在实际源列排序规则和目标 PG 规则下比较大小写、重音、Unicode、尾随空格和唯一键冲突。选择并记录可部署的 PostgreSQL collation 或明确的应用比较规则，验证登录、用户名创建/修改和 Open API；若无法在现有数据及支持的输入范围保持原语义，发布前需明确行为变更并处理冲突，不能仅依赖默认 collation。验证 `vite_config.name` 唯一性和其他业务比较与排序。
7. 更新或移除 `CodeGenerator.java` 的 MySQL 专用连接，确认生成器不会覆盖手工映射；审查 XML 别名并在需要时显式加双引号或 resultMap，保持 DTO 返回字段不变。

### 3. 安装、升级、备份和发布

1. 两份 Compose 改用 PostgreSQL 16、独立 `postgres_data` 卷、`POSTGRES_DB/USER/PASSWORD`、`pg_isready` 健康检查，后端依赖数据库健康；分别保留原 IPv4 / IPv6 网络配置。不要复用或删除 `mysql_data`，不发布数据库端口；通过应用查询再验证数据库可用性。
2. `panel_install.sh` 新安装下载同一版本的 PostgreSQL SQL、Compose 和后端镜像；已有初始化文件需核对版本/校验和，不能沿用同名旧 MySQL 文件。保留 `.env`、JWT 密钥和对外端口，避免改动现有登录及连接信息。
3. 更新流程在**下载覆盖、停止容器、拉取或启动之前**识别当前 Compose、运行容器、已有卷和数据库类型；发现 MySQL 或不确定状态就停止普通更新并明确引导迁移，绝不创建空 PostgreSQL 后报告升级成功。新旧脚本、手动 `docker compose up` 和直接更换镜像都需要在升级说明中警告；新版脚本无法拦截用户手动执行的旧脚本。对 PostgreSQL 更新先备份、执行版本化 DDL，再启动对应后端并核验；失败即停止，保留原文件与卷。
4. 导出改用 `pg_dump`，与 MySQL 原始备份明确区分格式和文件名；备份写入受限权限目录，失败不保留伪成功文件，避免在命令输出或进程参数中泄露密码。实现 PostgreSQL 恢复命令和空库恢复验证。卸载明确提示数据卷删除范围，迁移保留期内不得删除任一数据库卷。
5. 更新 `.github/workflows/docker-build.yml`：增加必需的 PostgreSQL 集成测试门禁，构建和发布对应后端镜像，更新两份 Compose、安装器和 SQL 的版本引用及 release 上传清单；更新 `README.md`，分别写新安装、现有实例迁移、备份恢复和回滚。先在临时 tag 上验证资源可下载，避免脚本指向未发布版本。

## 现有 MySQL 实例迁移与回滚

### 迁移前提

- 使用独立演练环境及脱敏或受控副本，记录数据库大小、导入耗时、停机窗口和磁盘余量；准备可恢复的 MySQL 一致性备份、原 Compose、`.env`、原镜像版本及卷名，备份应包含凭据与节点密钥的保护措施。验证恢复后再迁移。
- 导出实际 schema，核查所有历史表列、索引、版本及外部修改。以当前应用所需结构建立显式的源到目标字段映射：`user` → `app_user`、`user.user` → `app_user.username`，其余按实际表列映射。额外或废弃列先归档并由负责人确认；历史缺列的补值规则按版本逐项审核，不能调用会删列的旧升级脚本。
- 开发一次性迁移工具或使用经过演练的现有转换工具，明确版本、连接权限、字段转换和错误报告；以预建的目标结构为准，**仅复制数据**，不让工具自动创建不受控的表或种子。先实现并验证工具适配关键字映射、类型、空值、大文本、批次失败重试和无重复导入；若工具不能可靠做到则实现最小的专用导入程序。
- 明确停机期间流量策略：`FlowController` 接收节点上报并更新计数及状态，定时任务也会写入数据。迁移期间必须隔离全部写入，包括面板、开放 API、后台任务及节点上报。确认节点在连接失败时是否缓存/重试、是否可能重复或丢失；在证据不足时应暂停相关转发或接受并记录不可恢复的计费缺口，不能假设停面板等于流量停止。

### 执行步骤

1. 公告维护窗口，停止或隔离转发/上报和所有应用写入，确认无活动写事务，停止旧后端；保留 MySQL 和旧卷。对已静止源库做最终一致性备份并验证可读取，记录快照时刻和每表计数、主键范围、关键流量汇总。
2. 创建独立、空的 PostgreSQL 数据库，执行**不含种子**的建表脚本。使用经过演练的工具复制 8 张表，保留原 ID、密码摘要、节点 secret、JWT 配置、隧道和转发关系；失败即停止并丢弃此次隔离目标库后重试，不覆盖源库。
3. 按表对比总行数、主键集合、NULL 数量、关键数字汇总，以及按主键规范化后的全列内容/校验值；对用户名、配置值、长文本、中文、时间戳和密码摘要做精确比对，校验关联 ID 无新增孤儿及任何历史异常已记录。校验结果不得输出密码摘要和节点 secret。任何未解释差异均禁止切换。
4. 对每张表将 identity 序列设置到不低于最大已导入 ID 的安全位置，分别处理空表；在隔离副本验证插入、删除测试记录后下一次 ID 不冲突。对 `app_user` 和 `vite_config` 特别检查原种子 ID 与下一次 ID。验证唯一约束和实际 collation 冲突处理。
5. 使用新的后端和 Compose 指向 PostgreSQL，先保持外部写入及节点隔离，检查应用连接、登录、核心查询、管理员/普通用户权限和健康检查；确认无错误后重新接入，记录恢复时间。验证节点重新连接、配置下发及上报，并对迁移窗口的流量按前述策略核对。
6. 保存迁移日志、校验结果和版本信息；旧 MySQL 数据和备份保持只读及独立保留，至少覆盖约定观察期和回退决策窗口。不得直接清理旧卷。

### 回滚边界

- **PostgreSQL 尚无业务写入时**：停止新服务，恢复原 Compose、`.env`、旧镜像和原 MySQL 卷，确认 MySQL 状态与业务健康后开放流量。
- **PostgreSQL 已接收业务写入后**：旧 MySQL 已落后，直接切回会丢失新增/修改、流量和状态。先隔离全部写入并备份 PostgreSQL；只有完成经验证的 PostgreSQL → MySQL 增量/全量回迁并对账，或由实例负责人明确接受自切换时刻起的数据损失，才能恢复旧库。若回迁工具尚未实现和演练，优先在 PostgreSQL 上修复并恢复服务，不能宣称可无损回滚。
- 任何备份、迁移、验证或回退失败均停止操作并保留两侧数据；不要运行 `down --volumes` 或覆盖备份。

## 验收与发布门槛

| 类别 | 必须通过的检查 |
| --- | --- |
| 结构 | 空卷首次安装成功；8 表、约束、默认值与种子正确；空表和已有数据的自增 ID、批量插入均正常；重启和再次更新不重复初始化。 |
| 业务 | 登录/错误密码/禁用用户、创建与修改用户名及大小写比较、Open API、用户/节点/隧道/限速/转发 CRUD、分页与 JOIN DTO、配置读写均通过；请求与响应兼容。 |
| 流量 | 真实格式节点 ID 查询、非法 ID、并发上报的 forward/user/user_tunnel 原子计数、额度/过期处理、定时统计与重置、重连和窗口期上报行为通过；避免在生产节点上做破坏性测试。 |
| 数据 | 至少各演练一次新库及有代表性的历史库，完成全列对账、约束和主键序列检查；对 NULL、长文本、Unicode、边界值、历史 bigint、排序规则冲突及额外列给出结果。 |
| 运维 | IPv4/IPv6 Compose、旧 MySQL 升级阻断、下载资源一致性、备份恢复、新版 PostgreSQL 更新、故障中止、切换前后两种回滚路径分别演练；PostgreSQL 已写入的回迁若不支持，需明确记录限制并验收。 |
| CI/发布 | PostgreSQL 集成测试在 CI 实际执行并阻断失败；构建产物、release 资源及安装器引用同一版本；镜像及脚本在隔离环境完成端到端安装。 |

## 尚待验证与决策

本评估仅基于仓库静态阅读，没有运行 PostgreSQL、构建、集成测试或访问任何生产实例。实施前需确认实际历史版本分布、数据库规模、字符排序规则、节点断连时流量上报行为、可接受停机窗口及写入后回迁要求。只有完成上述证据和验收门槛，才能将可行性评估提升为可发布结论。
